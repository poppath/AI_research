# บท 12 · Operating Cadence — จังหวะงานที่ทำให้ระบบเดิน

> **Review 7 พ.ย. 2026:** เอกสารเดิมเป็น research snapshot มีตัวเลข/heuristic และข้ออ้างที่ยังต้องตรวจรายกรณี ไม่ใช่กฎสากลหรือ rate ปัจจุบัน; ก่อนใช้ให้ดู [ข้อจำกัดและรายการแก้ไข](../../REPO-REVIEW-2026-11-07.md) และ `AGENTS.md` โดยเฉพาะก่อนตัดสินใจงบ กฎหมาย หรือ automation.

## TL;DR

- Retention พังไม่ใช่เพราะขาดกลยุทธ์ แต่เพราะ **ไม่มีจังหวะงาน** — ไม่มีใครดู block rate รายสัปดาห์ ไม่มีใครรัน RFM รายเดือน
- จังหวะที่แนะนำ: **รายวัน 15 นาที · รายสัปดาห์ 60 นาที · รายเดือน 90 นาที · รายไตรมาสครึ่งวัน**
- KPI tree มี 4 ชั้น: business → retention → engagement → operational
- ทีมขั้นต่ำที่ทำให้ระบบเดินได้จริง = **2.5 คน** (คนแชท 1, คน CRM/content 1, หัวหน้า 0.5)
- ปฏิทินไทยต้องฝังในแผน: เงินเดือนออก, เทศกาล, mega sale, วันหยุดยาว

---

## 1 · จังหวะรายวัน (15 นาที)

**ใคร:** คนดูแลแชท / owner

```
□ ตรวจ first response time เมื่อวาน — มีแชทไหนค้างเกิน 1 ชม.
□ ตรวจออเดอร์ใหม่ + ปัญหาจัดส่ง/COD
□ ตรวจ auto-reply ว่ามีข้อความไหนตอบไม่ตรง
□ ตรวจ block/spam report (ถ้ามี)
□ tag แชทที่คุยจบเมื่อวานให้ครบ
```

**ห้ามทำรายวัน:** เปลี่ยน flow, เปลี่ยน rich menu, ส่ง broadcast (เพราะจะไม่มีข้อมูลพอตัดสิน)

---

## 2 · จังหวะรายสัปดาห์ (60 นาที)

**วาระมาตรฐาน**

| นาที | วาระ | ผลลัพธ์ |
|---|---|---|
| 0–10 | ตัวเลขสัปดาห์: เพื่อนใหม่, block rate, open rate, ยอดจาก LINE | รู้สถานะ |
| 10–20 | แชทที่ปิดไม่ได้ 3–5 เคส → root cause | 1 การแก้ไข |
| 20–30 | flow ที่ทำงาน: RPR, conversion, drop-off | 1 การปรับ |
| 30–40 | broadcast ที่ผ่านมา: RPM, CTR | ตัดสินใจคงไว้/แก้ |
| 40–50 | วางแผน broadcast สัปดาห์หน้า (กลุ่ม, ข้อความ, เวลา) | draft |
| 50–60 | งานค้าง + owner + deadline | action list |

**Output ที่ต้องได้ทุกสัปดาห์:** 1 การทดลองใหม่ + 1 การแก้ไข + ปฏิทินสัปดาห์หน้า

---

## 3 · จังหวะรายเดือน (90 นาที)

```
□ รัน RFM ใหม่ → ดูการเคลื่อนย้าย segment
□ ตรวจ block rate ราย segment → ปรับ cap
□ คำนวณ CAC, LTV₁₂, payback, MER
□ ดู cohort ใหม่ (เดือนที่แล้ว) เทียบ cohort เก่า
□ ทบทวน flow: มี flow ที่ RPR ต่ำต่อเนื่อง 2 เดือนไหม
□ ตรวจ quota usage + ค่าใช้จ่ายจริง vs แผน
□ ทบทวน rich menu / greeting / auto-reply
□ ตรวจ compliance: consent, opt-out, tag ที่ผิด
□ อัปเดต dashboard + ส่งรายงานผู้บริหาร
```

---

## 4 · จังหวะรายไตรมาส (ครึ่งวัน)

- recalibrate RFM threshold
- ทบทวน unit economics (COGS, fee, return rate เปลี่ยนไหม)
- re-verify ตัวเลข benchmark ทั้งหมด (`benchmarks.json`) — กฎ 90 วัน
- ทบทวน stack: เครื่องมือไหนไม่คุ้ม → ตัด
- วางแผนไตรมาสถัดไป: เป้า repeat rate, เป้า LTV:CAC
- ตรวจ PDPA/privacy notice

---

## 5 · KPI Tree

```
ชั้ น 1 — BUSINESS
  CM after ads · MER · LTV:CAC · payback

ชั้น 2 — RETENTION
  90-day repeat by source · time to 2nd order · cohort curve

ชั้น 3 — ENGAGEMENT
  open rate · CTR · block rate · RPM

ชั้น 4 — OPERATIONAL
  first response time · tag completeness · flow uptime · quota usage
```

**กฎ:** ถ้าชั้น 1 แย่ ให้ไล่ลงมาชั้น 4 — ไม่ใช่เริ่มแก้ที่ชั้น 1

## 6 · บทบาทและทีมขั้นต่ำ

| บทบาท | หน้าที่ | เวลา/สัปดาห์ |
|---|---|---|
| **Chat & Sales** | ตอบแชท, ปิดการขาย, tag | 30–40 ชม. |
| **CRM & Content** | flow, broadcast, segment, content | 20–30 ชม. |
| **Lead / Analyst (0.5)** | ตัวเลข, ตัดสินใจ, ประสาน | 10–15 ชม. |
| Support (outsource) | creative, dev, ที่ปรึกษา | ตามงาน |

**ลำดับการจ้าง**
```
1. คนตอบแชท (ถ้าตอบไม่ทัน = เสียเงินทุกวัน)
2. คนทำ content + flow
3. analyst / ที่ปรึกษา
```

## 7 · ปฏิทินไทยที่ต้องฝังในแผน

### รายเดือน
| ช่วง | พฤติกรรม | กลยุทธ์ |
|---|---|---|
| 25–1 | เงินเดือนออก | โปรหลัก, bundle |
| 2–10 | เงินตึง | เนื้อหา, ของเล็ก |
| 10–20 | ปกติ | cross-sell |

### เทศกาล/อีเวนต์
| เดือน | อีเวนต์ | ใช้ทำอะไร |
|---|---|---|
| ม.ค. | ปีใหม่ | ขอบคุณ + สิทธิ์ปีใหม่ |
| ก.พ. | วาเลนไทน์ | gift, couple set |
| เม.ย. | สงกรานต์ | gift ส่งต่างจังหวัด, ของขวัญผู้ใหญ่ |
| พ.ค. | เปิดเทอม | กลุ่มครอบครัว |
| มิ.ย.–ส.ค. | mid-year sale | ระบายสต็อก |
| ก.ย. | 9.9 | โปรใหญ่ |
| ต.ค. | 10.10 | โปรใหญ่ |
| พ.ย. | 11.11 | โปรใหญ่สุด |
| ธ.ค. | 12.12 + ปีใหม่ | โปรใหญ่ + gift |

### Mega sale ที่ต้องเตรียมล่วงหน้า 3–4 สัปดาห์
```
สัปดาห์ −4  วางแผน offer + สต็อก + segment
สัปดาห์ −3  ผลิต creative + ตั้ง flow
สัปดาห์ −2  tease (early access สำหรับ Champions)
สัปดาห์ −1  เตรียมทีมแชท + เพิ่ม quota ถ้าจำเป็น
วัน event  ส่ง 2–3 ครั้ง (เช้า/เที่ยง/ค่ำ) เฉพาะกลุ่ม
หลัง event  ขอบคุณ + flow 2nd purchase
```

**ข้อควรระวัง:** ช่วง mega sale block rate พุ่ง → ต้องเพิ่มคุณภาพการแบ่งกลุ่ม ไม่ใช่เพิ่มจำนวนครั้ง

## 8 · เอกสารที่ต้องมี

| เอกสาร | ใช้ทำอะไร | อัปเดต |

| Tag dictionary | มาตรฐาน tag ทั้งหมด | เมื่อเพิ่ม tag |

| KPI dashboard | 12 ตัวเลข | รายสัปดาห์ |
| Change log | ทุกการแก้ system | ทุกครั้ง |
| Consent register | หลักฐาน consent | ต่อเนื่อง |
| Incident log | ปัญหา + การแก้ | ทุกครั้ง |

## 9 · Escalation (L1–L5)

| ระดับ | สถานการณ์ | ใครรับ | SLA |
|---|---|---|---|
| L1 | คำถามทั่วไป | auto-reply / chat | ทันที |
| L2 | ปัญหาออเดอร์ | chat + ops | 4 ชม. |
| L3 | ข้อร้องเรียน / refund | หัวหน้า | 24 ชม. |
| L4 | วิกฤต (ข้อมูลรั่ว, ข่าวลบ) | owner + legal | ทันที |
| L5 | ระบบล่ม (webhook, OA) | tech + LINE support | ทันที |

---

## กับดักของบทนี้

- ❌ ไม่มีใครดู block rate
- ❌ รัน RFM ครั้งเดียวตอนเริ่ม
- ❌ วางแผน broadcast วันต่อวัน
- ❌ ไม่มี change log → หาสาเหตุไม่ได้เมื่อยอดตก
- ❌ ไม่เตรียมทีมแชทช่วง mega sale
- ❌ วัดตัวเลขแต่ไม่มีการตัดสินใจตามตัวเลข
